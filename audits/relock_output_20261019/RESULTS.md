## 结论

需要减少而不是增加状态机假说。25/29/31是审计脚本把独立字段拼出的标签，不是找到的游戏enum。全部533条29只出现一条保存记录，全部在31→29时Ps/Vs变化而完整rate逐分量复制。直接31→25也常出现同样的PV刷新/rate保留。因而无须先假设29有独立冷却；它可以是到期时输出来源和角状态有效性不同步的短暂组合。

新增实测区分：R77保持恢复中，58例明确早于一秒边界的普通端点关系误差中位数0.0373deg/s，而Q/.8重置不相容；22例近一秒边界、前后保存标签仍31的恢复中，19例与原固定Q/.8重置关系量化相容。即使没有保存29或25，内部也可能已经到期后重建，不能仅因输出仍31就强制不初始化。

但29→31本身没有被旧静态初始化统一解释：35例R77仅4例通过D_.8Q量化检验，RMS2.289deg/s；不能因此宣布整个初始化机制已恢复。#118在2.4375s旧检测器过早接受的根因仍未解决，本轮没有给held新增冷却。

## 1. 原始字段，而非擅自定义的模式

capture_held/audit.py的实际表达式：

code = type8*8 + flagA*4 + flagB*2 + flagC。

当前布局type8=3、flagC=1：25=(A0,B0)、29=(A1,B0)、31=(A1,B1)。timer后面的flag_after_timer0是另一个字段，不等同A/B。A/B确切语义未从游戏源码找到，也不能仅凭码值确定具体函数调用次数。仍叫code只是方便引用保存记录。

## 4. 同样是31 held→31 fresh，到期前后可能不是同一种更新

固定比较D(n)=.8I+.2nn^T、当前姿态Q；普通端点关系w1=w0+c/(.078525+T/2)，c由旧n按旧w预测到当前n的球面修正。没有拟合参数。当前n明确作为条件输出，不是独立雷达测量。

从旧timer加保存间隔估计状态年龄。明确早于边界：age<1−2/48−2*(10/32767)；边界带截至1+2/48+2*(10/32767)。这个留量在追加协议中固定，未按rate误差逐例选取。只比较两端flag0且新timer0的R77恢复。

19/22是值得保留的共同关系，不是所有22例成功：RMS由3个反例显著抬高，最大2.614181deg/s。未到期组普通公式也不精确，最大0.670065deg/s。未逐例挑选最优模型。

这使真正该区分的变量成为“内部跟踪是否已到期/重建”，而不是仅查看有没有保存25或29；两个输出仍31之间可以发生不可见的到期与重新初始化。当前数据支持这种解释，不直接证明游戏有哪个布尔变量或已恢复调用顺序。

## 6. 最小可解释流程（假说，不是生产补丁）

正常接受：更新当前track并重置观测年龄。
暂时无接受：保留旧角状态并传播方向，输出held；新的候选回波若仍满足该track的接受条件，则恢复普通更新，不统一冷却。
状态到期：原track的有效性结束，输出可转用另一份PV来源；旧角缓存可能暂时还在，产生29或直接25的记录组合。
到期附近重新建立：可能在保存前完成，因此输出也可能一直31；这时应走初始化而不是强行普通连续更新。
仍未建立：保留INS/搜索路径，在此前支持的全局搜索时刻尝试。搜索周期不是从每个held开始重新计时的一秒禁用。

这个流程只需区分已有track是否有效、角状态/回退PV来源及搜索尝试时钟，不必给29另造冷却。哪些回波满足恢复/重建接受条件，以及新PV来源，仍未恢复。#118在2.4375s的错误接受不能靠本轮输出分析自动消除；保持模型与真实观测历史不一致的失败仍保留。
